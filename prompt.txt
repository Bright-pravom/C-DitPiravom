## 1. Fix the course marquee overriding `prefers-reduced-motion` (accessibility + battery)

At the very bottom of `styles.css`, this rule exists:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: 0.01ms !important; ... }
}
/* The course strip is an intentional, continuously moving display. */
.marquee {
  animation: marquee-scroll 56s linear infinite !important;
  animation-duration: 100s !important;
  animation-iteration-count: infinite !important;
}
```

Because `.marquee` has higher specificity than the universal `*` selector, this **forces the marquee to keep animating even for users who have `prefers-reduced-motion: reduce` set** — the one animation on the entire site most likely to trigger motion sensitivity, running non-stop, un-disableable. It also means the marquee never stops animating even when scrolled off-screen, which costs CPU/battery on low-end Android continuously for as long as the tab is open.

- **Do:**
  - Remove the `!important` overrides on `.marquee`, or explicitly add `.marquee { animation: none; }` inside the existing `prefers-reduced-motion: reduce` block so it's respected like every other animation.
  - Pause the marquee animation when it's not in the viewport: use an `IntersectionObserver` on `.marquee-wrap` to toggle a class that sets `animation-play-state: paused` when it scrolls out of view, resuming when it scrolls back in. This alone meaningfully cuts background CPU use on long scroll sessions.
  - Keep the existing hover-to-pause behavior for desktop; the IntersectionObserver behavior is mobile-relevant since there's no hover there.
- **Verify:** with OS-level "reduce motion" enabled, the marquee is static. Scroll the marquee out of view in a mobile emulator and confirm (via DevTools Performance/rendering) that it's no longer animating while off-screen.

## 4. Add safe-area support for notches and gesture bars

No page currently declares `viewport-fit=cover`, and no CSS anywhere uses `env(safe-area-inset-*)`. On modern phones (notches, Dynamic Island, Android gesture bars) this means the floating WhatsApp button, the sticky header, and the mobile nav drawer can sit flush against or get clipped by the system UI.

- **Do:**
  - Update the `<meta name="viewport">` tag on **every** HTML page to: `<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover" />`. Do not add `maximum-scale` or `user-scalable=no` — pinch-zoom must remain available.
  - Add to `styles.css`:
    ```css
    :root {
      --safe-top: env(safe-area-inset-top, 0px);
      --safe-bottom: env(safe-area-inset-bottom, 0px);
    }
    ```
  - `.whatsapp-floating-button`: change `bottom` to `calc(<current-value> + var(--safe-bottom))` at both the base and the 760px-breakpoint override.
  - `.site-header` (if it's sticky/fixed — confirm in CSS) and `.mobile-nav`: add `padding-top: var(--safe-top)` where they sit at the very top of the viewport.
  - If the mobile nav or bottom sheet (from Task 2) has bottom-anchored action buttons, give their container `padding-bottom: calc(20px + var(--safe-bottom))`.
- **Verify:** in a simulator/device with a bottom gesture bar or notch, the WhatsApp button and any bottom sheet actions have visible clearance, not flush against the system UI.
